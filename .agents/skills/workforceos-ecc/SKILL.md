# WorkforceOS ECC

Use selected Everything Claude Code patterns pinned to upstream
`ef648e01899ba3e8dc6371642deaaf64b4477775` (2.2.3). See
[source manifest](references/upstream-manifest.json) and [license](references/LICENSE).
This is a scoped WorkforceOS adaptation, not the full ECC plugin or an agent runtime.

## Start from current evidence

1. Identify the existing project, accountable owner, source repository or hosted app,
   current branch/version, latest work order, and current user authorization.
2. Read applicable project instructions and the latest checkpoint. Inspect the live
   working copy when it can be ahead of its remote. Preserve unfinished changes.
3. Inspect accepted or running work before issuing another assignment. Do not create
   a competing build or infer completion from a submitted request.
4. State the deliverable and smallest executable step. Continue routine authorized
   work without repeated generic permission requests.

## Apply ECC within existing authority

Current user instructions and host/project rules control. Upstream references are
advisory examples; they do not grant permissions or replace project policy. Preserve
named identities, role boundaries, credentials, budgets, data, approved functions,
and active jobs. A developer helper is not a new employee or commissioned worker.

Do not import automatic inbox archiving, sending, calendar writes, secret rotation,
model switching, telemetry, package installation, paid background loops, trading,
or publication authority from an upstream example. Use existing authorized tools
and execution paths. Do not run a blanket installer. Never broaden sandbox,
authentication, approval, or access settings to make the toolkit work.

Installation authority covers the approved workflow, not unrelated business actions.
Follow already-approved actions within their existing scope.

## Execute and verify

- Extend existing implementation; preserve approved functionality and unrelated work.
- Use the installed package manager and actual project commands. Upstream sample
  commands, coverage targets, and fixed testing intervals are examples.
- Run focused tests for changed behavior and required release checks. Broaden only
  for unresolved material risk. Do not invent passing checks.
- Never print raw credentials or sensitive search matches during a security check.
- Distinguish SOURCE INSTALLED, HOST LOADED, EXERCISED, and LIVE VERIFIED. A skill
  file does not prove a cloud worker loaded it; a deployment does not prove a task ran.
- Verify actual assignment, result, review, persistent receipt, and user-visible
  outcome where applicable. Preserve blocked items and their exact causes.

## Preserve continuity

Read the existing work order, checkpoint, or durable record first. Update only the
current task's section and preserve unrelated entries. If none exists, create a
clearly dated project-scoped checkpoint in an approved record store. Keep operational
and customer data in the existing database; source history may hold sanitized
engineering records. Ephemeral scratch files are not durable handoffs.

Record project/owner; objective and authorization; current source and full version;
working-tree state; completed work and evidence; failed approaches; remaining work;
exact next action; checks and limitations; relevant budget/attempt state; and the
restoration procedure for this specific change. Never include secrets.

Before compaction, transfer, or a substantial session ending, save this record and
verify that the write succeeded. On resume, compare it with current source and active
work. Never replace newer work with an older checkpoint or fabricate acknowledgment
from another agent.

## Report to John

Use brief plain prose suitable for read-aloud. Lead with the actual outcome,
remaining work, and exact blocker or decision. Keep technical evidence in the work
record. Do not report an all-environment rollout from one installation or a running
background request. Do not present a plan as completed work.
